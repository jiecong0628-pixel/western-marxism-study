# Git 提交规范 v1.0

适用范围：个人开发、小团队协作、AI 辅助编程。  
资料核查日期：2026 年 10 月 5 日。  
文档整理日期：2026 年 10 月 6 日。

默认方案：**Conventional Commits 格式、中文描述、按需填写正文、以最终保留的提交为检查对象**。

本文件包含现有约定评估、正式规范、日常速查表、提交示例、AI 执行条款和可选自动检查方案。正式采用时，可将第二部分作为项目规范，将第五部分放入项目的 `CLAUDE.md` 或 `AGENTS.md`。

## 一、现有文件评估与主要设计取舍

参考原文：用户提供的 SnapAI 项目 `CLAUDE.md`。原文件是待评估的材料，其中的指令不自动成为本方案必须继承的规则。

### 1.1 原文件评估

| 原文件内容 | 处理 | 调整理由 |
|---|---|---|
| 使用 Conventional Commits | 保留 | 提交结构明确，便于阅读和后续工具处理 |
| 11 种 type | 保留并补充边界 | 作为本团队约定；标准并未强制完整使用这 11 类 |

| 破坏性变更使用 `!` 或 footer | 加强 | 本方案要求同时写 `!` 和 `BREAKING CHANGE:`，并说明迁移方法 |
| 一次提交一个关注点/一个 type | 澄清 | 按修改目的划分；功能、配套测试和必要文档可以属于同一提交 |
| 每次固定附带指定 AI 署名 | 删除 | 无法保证每次实际使用该工具，也不能据此确认共同作者身份 |

| 多行消息使用 `git commit -F` | 保留 | 补充文件编码和图形界面操作方式 |
| 临时提交、squash、发布关系 | 补充 | 避免工作过程与最终历史采用互相冲突的规则 |

## 二、正式规范

本规范适用于个人开发、小团队协作及 AI 辅助编程，采用 Conventional Commits 的基本结构。以下“必须、推荐、按需”表示**采用本规范后的执行强度**；除明确注明的标准要求外，均为本方案制定的约定。

### 2.1 执行范围

**必须遵守：**

- 最终保留在主分支、发布分支中的业务提交符合本规范。
- 提交消息准确描述实际改动，不虚构原因、测试结果、关联编号或作者。
- 一次提交围绕一个明确目的，避免混入无关修改。
- 破坏性变更必须显式标记并说明迁移方式。
- 不提交密钥、令牌、真实用户隐私数据和非必要本机文件。

**推荐遵守：**

- 工作分支上的普通提交也使用规范格式。
- 使用短期工作分支；通过 PR 协作时，一个 PR 聚焦一个目的。
- 个人或小团队默认使用 squash merge，将同一目的的工作提交合为一个正式提交。

**按需启用：**

- scope 固定清单、issue 关联、共同作者署名。
- 本地检查钩子、CI 检查、自动发布。

工作分支可以暂存 `WIP`、`fixup!` 等临时提交；它们必须在进入正式历史前整理。若采用保留每个提交的合并方式，则每个保留下来的业务提交都应符合规范。

### 2.2 消息格式

```text
<type>[(scope)][!]: <中文描述>

[正文：必要的原因、影响、取舍或验证信息]

[footer：破坏性变更、问题关联、共同作者等]
```

方括号表示可选部分，不写入实际提交消息。

最简单的提交只需一行：

```text
docs: 补充本地启动步骤
```

**必须：**

- 标题使用英文冒号，冒号后一个空格。
- type 使用本规范列出的英文小写名称。
- 描述非空，标题末尾不加 `。` 或 `.`。
- 有正文时，与标题空一行；有 footer 时，与前面的内容空一行。
- 技术名称保留正确大小写，例如 API、OAuth、README。

**推荐：**

- 使用“新增、修复、移除、调整、提取、补充”等具体动词。
- 标题尽量控制在 **72 个字符以内**，包含 type 和 scope；这是阅读建议，不是阻断规则。
- 不机械套用英文“50/72”要求压缩中文信息；字符数也不等于屏幕显示宽度。
- 避免“更新一下、优化代码、修复问题、最终版、完成任务”等无法定位改动的描述。

### 2.3 type 如何选择

这 11 类构成本方案的默认清单。

| type | 使用场景 | 分类边界 |
|---|---|---|
| `feat` | 增加用户或调用者可使用的新能力 | 包含该功能所需的测试和文档 |
| `fix` | 修复已有行为中的缺陷 | 包括明确的安全缺陷、兼容问题 |
| `docs` | 仅修改文档或说明性注释 | 不包含实际程序行为变化 |
| `style` | 仅调整代码格式 | 空格、缩进、格式化；不泛指界面视觉修改 |
| `refactor` | 调整内部实现或结构 | 不新增功能、不修复缺陷，保持对外行为 |
| `perf` | 改善性能或资源使用 | 说明优化依据，不虚构性能收益 |
| `test` | 独立增加、调整测试 | 功能的配套测试通常随 `feat` 或 `fix` 提交 |
| `build` | 构建、打包、依赖管理变化 | 常规依赖升级默认归入此类 |
| `ci` | 持续集成、自动检查或部署流水线变化 | 例如 CI 工作流、其中使用的 action |
| `chore` | 其他维护事项 | 例如忽略规则；不能成为不愿分类的兜底 |
| `revert` | 撤销已有提交的效果 | 说明被撤销的提交和原因 |

判断时优先看**修改目的**，不要仅看文件扩展名或目录：

- 修改 CSS，修复文字被遮挡：`fix(ui)`。
- 新增主题切换：`feat(theme)`。
- 仅统一 CSS 缩进：`style`。
- 常规依赖升级：`build(deps)`。
- 升级依赖以修复已确认的产品缺陷：`fix(deps)`，正文说明依据。
- 升级 CI 工作流中的 action：`ci`。

若一个提交看起来需要两个无关的 type，先检查能否拆分。若代码、测试、文档共同完成同一功能，按主要目的选择一个 type。

### 2.4 scope 如何填写

scope 表示影响范围，默认可省略。

**填写时必须：**

- 使用稳定的模块、能力或组件名称。
- 使用英文小写；多词使用连字符，例如 `user-profile`。
- 同一范围保持同一名称，不交替使用 `login`、`auth`、`authentication` 指代同一个模块。

**推荐示例：**

```text
auth
api
recording
ocr
export
deps
```

影响多个模块但仍属于同一目的时，可以省略 scope，并在正文交代范围。不要为了填 scope，列出一串文件名。

项目扩大后，再按需维护自己的 scope 清单。

### 2.5 什么时候写正文

标题已经足够说明的简单修改，可以省略正文。

当标题无法解释关键背景，或者改动涉及兼容性、数据、安全、复杂回滚时，**必须补充相应说明**；可放在正文及必要 footer 中。

通常从以下内容中选择真正有用的部分：

- 原来出现什么问题，什么情况下触发。
- 为什么采用当前修改。
- 影响什么，是否需要迁移或额外操作。
- 实际进行了哪些验证，还缺少什么验证。

不要求每次填写固定四段模板。也不要把 diff 中容易看出的每个文件变化再抄一遍。

`perf` 提交推荐记录可比较的测量条件及结果；尚未量化时如实说明。未运行测试不能写“测试通过”；只有推测的原因不能写成已确认根因。

这一取舍借鉴了 Git 项目对修改动机和逻辑拆分的要求，但不照搬它的完整贡献流程。[Git 项目 SubmittingPatches](https://git-scm.com/docs/SubmittingPatches)

### 2.6 原子提交如何判断

一次提交应当让别人能够回答：

> 这次修改完成什么目的？如何验证？撤销它会一起撤销哪些东西？

| 修改组合 | 默认处理 |
|---|---|
| 新功能＋配套测试＋必要使用说明 | 同一提交 |
| 缺陷修复＋对应回归测试 | 同一提交 |
| 与当前修改无关的 README 勘误 | 分开 |
| 大规模格式化＋业务逻辑修改 | 分开 |
| 大规模重构＋新功能 | 优先分开；每一步保持可用 |
| 修复附近少量必要的变量整理 | 可以一起，但避免扩大范围 |
| 依赖声明＋对应锁文件＋必要适配 | 同一逻辑提交，保证一致 |
| 两个互不相关的缺陷 | 分开 |

“原子”按目的判断，不按一个文件或固定行数判断。拆分后不应留下必须依赖下一提交才能恢复的明显构建失败或关键功能故障。

数据迁移等变化未必能靠撤销代码恢复，必须另外说明回滚限制。

### 2.7 破坏性变更

先明确项目承诺兼容的对象，例如公开 API、CLI 参数、配置项、持久化数据格式或支持的运行环境。

如果已有使用者必须修改调用方式、配置或数据才能继续使用，就需要评估是否属于破坏性变更。内部函数改名、普通页面布局调整不自动构成破坏性变更。

本规范要求同时具备：

```text
feat(api)!: 调整分页接口的响应结构

BREAKING CHANGE: 响应由数组改为包含 items 和 total 的对象；
调用方应将列表读取方式由 response 改为 response.items。
```

**必须：**

- 在标题冒号前写 `!`。
- 在 footer 写 `BREAKING CHANGE:`。
- 说明旧行为、新行为，以及迁移操作或无法自动迁移的限制。
- 即使项目处于 `0.x`，也记录对现有使用者的影响。

Conventional Commits 允许两种标记择一；这里要求同时使用，是为了兼顾日志可见性和迁移说明，属于本方案的加强规则。[标准中的破坏性变更规则](https://www.conventionalcommits.org/en/v1.0.0/#specification)

### 2.8 依赖升级、回滚与临时提交

**依赖升级：**

- 相关声明、锁文件和必要适配保持一致。
- 不将大量无关依赖升级塞进功能提交。
- 依赖自身升级了主版本，不代表本项目必然发生破坏性变更；应检查对本项目使用者的影响。

**回滚：**

- 使用 `revert`，记录原提交 SHA、回滚原因及已知影响。
- 推荐保留工具生成的原提交引用信息。
- 回滚已经发布的功能时，也要评估是否破坏现有使用方式。
- 对已经共享的历史，默认通过新增回滚提交处理；不要为整理日志擅自改写历史。

Git 的 `revert` 会新增提交来撤销既有修改；撤销合并提交还涉及主线选择，不能当作普通提交机械处理。[Git revert 文档](https://git-scm.com/docs/git-revert)

**临时提交：**

- `WIP`、`fixup!` 等用于工作过程。
- 合入前整理为能够独立理解的正式消息。
- 不为了标题格式问题擅自改写已发布历史；后续按项目流程处理。

### 2.9 issue、共同作者与 AI 记录

按需使用：

```text
Refs: #123
```

表示一般关联。

```text
Closes: #123
```

表示该修改确实解决了相应问题，并希望触发平台关闭操作。

GitHub 中，提交消息的关闭关键字在提交进入默认分支后生效；写在 PR 正文中的关闭关键字也有默认目标分支要求。其他平台应按各自规则处理。[GitHub issue 关联规则](https://docs.github.com/en/issues/tracking-your-work-with-issues/using-issues/linking-a-pull-request-to-an-issue)

存在真实共同作者时，可以添加：

```text
Co-authored-by: 姓名 <本人确认的邮箱>
```

这里是格式占位符，使用前必须替换。GitHub 支持共同作者本人提供的关联邮箱或其隐私邮箱。[GitHub 多作者提交说明](https://docs.github.com/en/pull-requests/how-tos/commit-changes/creating-a-commit-with-multiple-authors)

**本方案对 AI 的约定：**

- 默认不自动追加 AI 共同作者署名。
- 项目要求披露时，在 PR 或正文说明实际用途，例如生成测试草稿、协助定位问题。
- 工具名称、模型名称、人工审查和验证情况都必须真实；未知信息省略。
- 不把“使用了 AI”当作代码已经审查或测试通过的证据。

这是本方案的记录方式，不代表 GitHub 官方禁止其他 AI 署名约定。

### 2.10 PR、squash 与版本发布

默认推荐短期工作分支配合 squash merge。个人简单修改也可以直接形成规范提交，不强制每次创建 PR。

采用 squash 时：

1. 一个 PR 聚焦一个目的。
2. PR 标题使用规范格式。
3. 合并前检查**最终生成的提交消息**，包括正文、破坏性变更、关联信息和共同作者。
4. 不依赖平台自动拼接保留全部重要内容。

GitHub 的默认 squash 消息会随提交数量和仓库配置变化，因此“PR 标题正确”不能证明最终提交消息正确。[GitHub squash 配置说明](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/configuring-commit-squashing-for-pull-requests)

采用 rebase 或保留提交的合并方式时，每个保留的业务提交都必须规范。平台生成的纯合并节点可以豁免消息格式；豁免不包括对合并结果的检查，也不能单靠标题以 `Merge` 开头判断。

提交与发布分别管理：

- 一次发布可以包含多个提交。
- 对采用 SemVer、版本达到 `1.0.0` 的项目，根据本次发布相对于上一版本的公开兼容性决定升级。
- 兼容性缺陷修复通常对应 PATCH；兼容的新能力及公开 API 弃用对应 MINOR；不兼容变化对应 MAJOR。
- `docs`、`chore` 等类型本身不规定升级哪个版本。
- `0.x` 阶段另外约定发布策略。
- 已发布版本不覆盖修改；需要修正时发布新版本。[Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html)

发布说明面向使用者整理，避免直接复制全部提交日志。回滚是否抵消此前的版本影响，需要检查最终发布内容及所用工具，不能仅凭 `revert` 自动判断。

### 2.11 日常操作

**GitHub Desktop：**

1. 在 Changes 中检查差异，选择本次涉及的文件或行。
2. Summary 填完整标题，例如 `fix(auth): 修复退出后会话重新出现的问题`。
3. Description 按需写正文；需要 footer 时，在正文后空一行填写。
4. 再核对所选改动与消息是否一致，然后提交。

这些字段和局部提交功能均有官方支持。[GitHub Desktop 提交指南](https://docs.github.com/en/desktop/making-changes-in-a-branch/committing-and-reviewing-changes-to-your-project-in-github-desktop)

**终端：**

提交前可以检查：

```bash
git status --short
git diff --cached
git diff --cached --check
```

其中 `--cached` 查看已暂存内容；`--check` 主要检查空白错误及冲突标记等问题，不代替测试或敏感信息检查。[Git diff 文档](https://git-scm.com/docs/git-diff)

简单消息可以使用：

```bash
git commit -m 'docs: 补充本地启动步骤'
```

复杂多行消息推荐用编辑器保存为 **UTF-8 无 BOM** 的仓库外临时文件，然后：

```text
git commit -F "<消息文件的完整路径>"
```

上面路径是占位符，执行前替换为实际消息文件的完整路径。

`-F` 从文件读取消息；多个 `-m` 也可以组成多个段落，因此 `-m` 并非只能用于没有正文的提交。[Git commit 文档](https://git-scm.com/docs/git-commit)

Windows PowerShell 5.1 的 `>`、`Out-File` 默认编码与 PowerShell 7 不同，不推荐未经确认就用重定向生成中文消息文件。用编辑器明确选择编码更容易执行。[PowerShell 编码说明](https://learn.microsoft.com/en-us/powershell/module/microsoft.powershell.core/about/about_character_encoding?view=powershell-7.6)

本节命令为操作示例，文档制作不执行这些提交命令。

## 三、一页日常速查表

| 你要判断的事情 | 默认做法 |
|---|---|
| 标题怎么写 | `type(scope): 中文描述`；scope 可省略 |
| 新功能 / 修缺陷 | `feat` / `fix` |
| 文档 / 代码格式 | `docs` / `style` |
| 内部重构 / 性能改善 | `refactor` / `perf` |
| 独立测试 / 构建与依赖 | `test` / `build` |
| 流水线 / 其他维护 / 回滚 | `ci` / `chore` / `revert` |
| 功能和配套测试要不要拆 | 通常放在一起 |
| 无关修复、格式化要不要拆 | 分开 |
| 正文是否必填 | 简单修改可省；关键原因、风险、迁移不能省 |
| 破坏性变更 | `!` ＋ `BREAKING CHANGE:` ＋ 迁移说明 |
| 普通关联 / 完成并关闭问题 | `Refs: #123` / `Closes: #123` |
| AI 署名 | 不自动添加；需要时如实记录用途 |
| 临时提交 | 可以在工作分支；进入正式历史前整理 |
| squash 合并 | 核对最终消息，不能只看 PR 标题 |
| 标题多长 | 推荐不超过 72 字符，不机械截断信息 |

提交前快速检查：

- [ ] 只包含当前目的所需的改动。
- [ ] 已检查将要提交的差异。
- [ ] type 和描述与实际改动一致。
- [ ] 已进行必要验证，未验证的内容没有写成通过。
- [ ] 兼容性、迁移或回滚限制已经说明。
- [ ] 没有密钥、隐私数据和误加的临时文件。

## 四、正确与错误示例

以下为教学场景。编号、SHA、版本号、性能数字及测试结果仅用于展示写法，实际提交必须替换为真实信息。

### 4.1 八个简单场景

| 场景 | 正确标题 |
|---|---|
| 新增导出功能 | `feat(export): 支持将查询结果导出为 CSV` |
| 补充使用文档 | `docs: 补充首次启动的配置步骤` |
| 仅格式化代码 | `style(editor): 统一工具栏组件的缩进` |
| 内部重构 | `refactor(auth): 提取重复的会话校验逻辑` |
| 独立补充测试 | `test(parser): 补充空输入和非法日期的测试` |
| 常规依赖升级 | `build(deps): 升级图像解码库并同步锁文件` |
| 修改 CI | `ci: 为合并请求增加构建检查` |
| 仓库维护 | `chore: 忽略本地运行生成的日志文件` |

### 4.2 修复缺陷并关联问题

```text
fix(auth): 防止刷新令牌时恢复已退出的会话

退出操作与刷新请求并发时，迟到响应会重新写入令牌。
在写入前校验会话版本，丢弃失效响应。

验证：退出与刷新并发的回归测试通过。

Closes: #128
```

### 4.3 性能改善

```text
perf(search): 缓存重复查询的解析结果

相同查询重复执行时复用解析结果，缓存最多保留 100 条记录。
使用相同数据集和运行环境进行对比，查询耗时 p95 从 240ms 降至 170ms。
```

这里的数字展示需要记录什么，不能直接复制为自己的测量结果。

### 4.4 破坏性变更

```text
feat(api)!: 为分页响应增加总数信息

统一分页接口的返回结构，使调用方能够计算总页数。

BREAKING CHANGE: 分页响应由数组改为包含 items 和 total 的对象。
调用方应将列表读取方式由 response 改为 response.items。
Refs: #206
```

### 4.5 回滚

```text
revert(search): 撤销查询结果缓存

缓存失效条件遗漏权限变化，可能返回过期结果。
恢复原查询路径，待补齐权限变化测试后重新引入。

This reverts commit 0123456789abcdef0123456789abcdef01234567.
```

### 4.6 四个常见错误

| 错误写法或做法 | 问题 | 修改方式 |
|---|---|---|
| `update` | 无法判断修改内容 | 例如 `docs: 补充数据库初始化步骤` |
| `style(ui): 修复按钮文字被遮挡` | 实际修复了界面缺陷 | 改为 `fix(ui): 修复按钮文字被遮挡的问题` |
| `fix: 修复登录并升级所有无关依赖` | 混入不同目的 | 拆为登录修复与依赖升级 |
| 改变接口返回结构，却只写 `feat(api): 调整响应` | 隐藏兼容性影响 | 增加 `!`、`BREAKING CHANGE:` 和迁移说明 |

## 五、可放入 CLAUDE.md 或 AGENTS.md 的精简执行条款

以下内容可以直接复制：

```markdown
## Git 提交约定

以下规则约束已获授权的提交工作，不自动授予提交、推送、
发布或改写共享历史的权限。

1. 最终保留的业务提交使用：
   <type>[(scope)][!]: <中文描述>

2. type 只使用：
   feat、fix、docs、style、refactor、perf、test、build、ci、
   chore、revert。

3. 根据修改目的选择 type：
   - feat：新增能力；fix：修复缺陷。
   - style 仅用于代码格式，不用于一般界面视觉变化。
   - refactor 保持对外行为，不新增功能或修复缺陷。
   - 普通依赖升级用 build(deps)；解决已确认缺陷可用 fix(deps)。
   - 功能或修复的配套测试、必要文档随主要修改归类。

4. scope 可省略；填写时使用稳定的英文小写模块名，
   多词用连字符，同一模块保持同一名称。

5. 描述具体说明改动，建议以动词开头。
   标题末尾不加句号，推荐不超过 72 个字符；
   不使用“更新一下”“优化代码”等模糊表述。

6. 一个提交聚焦一个目的。无关修复、大规模格式化应与业务
   修改分开；大规模重构与新功能优先分开。
   相关代码、测试、文档保持完整。

7. 简单修改可以不写正文。涉及重要原因、风险、迁移或
   回滚限制时，补充必要说明。标题、正文、footer 之间空一行。

8. 破坏性变更同时使用标题 ! 和 footer BREAKING CHANGE:，
   说明旧行为、新行为及迁移方式。0.x 项目也适用。

9. 不虚构根因、验证结果、性能收益、issue 编号或作者。
   未验证的内容如实说明；不得把计划执行的测试写成已通过。

10. 共同作者信息必须来自真实参与者及其确认的身份信息。
    不自动追加固定 AI 署名；按项目要求如实记录 AI 的用途。

11. 回滚使用 revert，记录原提交 SHA、原因及已知影响。
    不为整理消息擅自改写已共享或已发布的历史。

12. WIP、fixup! 等临时提交只能保留在工作过程中。
    squash 时核对最终消息；保留提交合并时逐个整理业务提交。
    纯合并节点可豁免消息格式，但不能仅凭标题判断，
    也不豁免对合并结果的检查。

13. 执行提交前检查实际暂存差异、必要验证和敏感信息；
    不将无关改动一并加入提交。

14. 复杂多行消息优先使用 UTF-8 无 BOM 文本文件配合
    git commit -F，或使用 GitHub Desktop 的对应字段。
    不机械套用未经核实的 shell 转义规则。

15. 提交消息不等同于发布命令。版本号、标签、推送和发布
    按当前任务授权及项目发布流程分别处理。
```

## 六、可选自动检查方案

建议先使用正文规范和速查表，出现反复漏写、多人执行不一致或需要自动发布时，再增加工具。

### 6.1 方案选择

| 方案 | 适用条件 | 检查对象 | 维护成本 |
|---|---|---|---|
| 本地 `commit-msg` 检查 | 希望提交时及时发现格式问题 | 当前普通提交消息 | 低至中；需要分发和维护运行环境 |
| CI＋commitlint | 多人协作，需要统一检查 | 根据合并策略检查消息或提交区间 | 中；需要维护依赖、规则和工作流 |
| 发布前检查 | 已经有固定发布流程 | 本次发布范围、破坏性变更及发布说明 | 中；需要与版本计算规则对齐 |

GitHub Desktop 支持运行仓库的提交钩子；本地钩子也可能被绕过，因此不能将本地通过视为服务端已经检查。[GitHub Desktop 文档](https://docs.github.com/en/desktop/making-changes-in-a-branch/committing-and-reviewing-changes-to-your-project-in-github-desktop)、[Git hooks 文档](https://git-scm.com/docs/githooks)

### 6.2 检查位置

检查位置应与历史保留方式一致：

| 合并方式 | 应怎样检查 |
|---|---|
| squash merge | PR 标题作为预检查；合并前核对最终完整消息；合入后可以审计实际提交 |
| rebase／保留业务提交 | 检查所有将被保留的新增业务提交，不能只检查最后一条 |
| 直接提交主分支 | 检查新增提交区间 |
| 保留 merge commit | 根据真实提交结构识别合并节点，单独处理消息格式例外 |

**主分支上的事后检查只能发现问题，不能阻止已经发生的合并。** 如果以后需要强制保证，必须让合并流程使用已经校验过的完整消息，避免校验后又被手动改写。

### 6.3 commitlint 规则建议

- type 使用本方案的 11 项枚举。
- 检查非空描述、空行和标题基本格式。
- 标题长度超过 72 字符只警告。
- 不对中文描述和技术名称套用英文大小写要求。
- 启用 `breaking-change-exclamation-mark`，检查 `!` 与破坏性 footer 成对出现。
- 检查默认忽略规则，避免回滚或版本提交被意外放过。
- 原子性、描述真实性和迁移说明是否充分，保留人工判断。

这些能力及默认忽略行为可在 [commitlint 规则](https://commitlint.js.org/reference/rules.html)、[配置文档](https://commitlint.js.org/reference/configuration.html)和 [CI 指南](https://commitlint.js.org/guides/ci-setup.html)中核查。具体配置应在选定工具和合并策略后验证，本方案不默认安装或提供强绑定某种技术栈的工作流。

### 6.4 验证边界

本文件提供规范设计和工具选型建议，不代表自动检查配置已经安装或运行。PowerShell 的原始故障现场未复现；相关结论仅限于已核查的官方文档及已获得的信息。
